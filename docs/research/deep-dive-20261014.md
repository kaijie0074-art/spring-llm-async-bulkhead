# 自主深潜研究：同步 LLM 线程池隔离 vs 真实推理尾延迟 · 2026-10-14

- 方法：每轮=可实验验证的问题 → 最小实验（真实 LLM 或确定性离线副本）→ 数据 → 结论/修复。
- 真实端点：`https://open.bigmodel.cn/api/coding/paas/v4`，模型 glm-4-flash，探针 `scripts/research/probe_latency.py`（串行 + 间隔 2s + 429 退避 60s×3，原始数据见 `evidence/*.jsonl`）。
- 离线副本：`scripts/research/fake_llm.py`（26s 固定延迟 + 429 剧本开关），驱动真实 jar 做参数扫描，零 API 配额、确定性。

## Q1 真实延迟到底什么分布？12s 的 read 超时切掉了多少？

**假设**：昨日单次 26s 不是离群而是分布的一部分；延迟由模型生成行为主导，12s read 超时会切掉大量真实成功。

**实验**：同一提示词（仓库请求体原文 `请优化简历 r-1`，不带 max_tokens）串行 12 次，记录延迟与 usage。

**数据**（`evidence/latency-q1-default-20261014.jsonl`，12/12 成功，0 次 429）：

| 指标 | 值 |
|---|---|
| P50 | **20090 ms** |
| P95 | **47541 ms** |
| min / max | 2111 / 47541 ms |
| completion_tokens | 40–716（mean 279，**同一提示词 18 倍离散**） |
| 生成速率 | 13.4–24.2 tok/s（mean 18.0） |

按经验 CDF：read=12s 成功率 **6/12=50%**；25s→75%；32s→92%；48s→100%。

**结论**：
1. "单调用 ≈26s"实为 **P50≈20s、P95≈47.5s 的重尾分布**，且尾部由**模型自己决定写多长**（40–716 token 非确定）——输出长度非确定性是 LLM 依赖与普通 IO 依赖的本质区别。
2. 默认 `read-timeout-ms=12000` 在真实 glm-4-flash 下砍掉约半数本可成功的调用；fixed 模式的"保护"在默认配置下同时意味着"放弃约一半的 AI 成功率"。
3. `finish_reason` 全部 stop：慢不是错误，是模型在认真写。

## Q2 延迟能否用工程手段压缩？分解 TTFT 与生成速率

**假设**：延迟 ≈ TTFT + tokens/速率；若 TTFT 小、速率有硬上界，则压缩延迟的唯一杠杆是输出长度。

**实验**：
1. max_tokens 扫描：32、128 各 4 次（`evidence/latency-q2-mttokens-20261014.jsonl`）；
2. 流式 2 次直测 TTFT（`evidence/latency-q2-stream-20261014.jsonl`）；
3. 对 Q1+Q2 共 18 个成功样本做 latency ~ completion_tokens 回归。

**数据**：

| 实验 | 结果 |
|---|---|
| max_tokens=32 ×4 | 1.44–2.26s（32 tok 全部 `finish_reason=length` 截断） |
| max_tokens=128 ×4 | 3.7–7.5s（3/4 `length` 截断；1 次模型只写 55 tok 自然 stop） |
| 流式 TTFT ×2 | **571 ms / 952 ms**，总时长 25.8s/21.0s |
| 回归（n=18） | latency = tokens × **61 ms** + ≈0s，Pearson **r=0.974** → 速率 ≈ **16.4 tok/s** |

**结论**：
1. 延迟几乎 100% 由生成 token 数决定（r=0.974，截距≈0，TTFT<1s）——**16.4 tok/s（13–24 区间）是模型侧硬速率**，非网络问题。
2. `max_tokens` 是线性有效的延迟旋钮（32→~2s），但以截断为代价；`finish_reason=length` 是质量损失的直接证据。
3. 换更快的网关/连接池/压缩提示词都动不了这个斜率——**工程能改变失败的速度，改变不了生成的速度**。

## Q3 超时分层：connect/read/deferred 三个时钟各管什么？

**假设**：read 超时是资源释放时钟 + 熔断失败信号源；deferred 是用户等待时钟，两者解耦；read 设在依赖 P99 以下会把"慢"误判为"坏"，触发熔断假宕机。

**实验**：
1. 真实 API 三档 read（12s/25s/40s，deferred=read+5s），服务 fixed 模式，optimize 并发 2 / login 并发 4 / 80s（`evidence/q3-timeout-sweep-20261014/`）；
2. 离线确定性病理演示：fake 上游 40s、read=40s、deferred=15s —— 用户先超时，池线程钉多久？（`scripts/research/demo_timeout_layering.py`）

**数据 1（真实 API）**：

| read | optimize 结果分布 | 用户侧成功 | login P99 |
|---|---|---|---|
| 12s | 56570 次：200×1 / 503×56556 / 504×13 | **0.002%** | 27 ms |
| 25s | 22963 次：200×3 / 503×22955 / 504×5 | **0.013%** | 27 ms |
| 40s | 6 次：200×6，P50 26.6s / P99 33.8s | **100%** | 27 ms |

**发现（Q3 核心）**：read=12/25s 时上游真实成功率 50–75%（Q1 CDF），但超时被熔断记为失败 → 熔断 OPEN → **用户侧成功率跌到 0.002–0.013%**——熔断把"慢依赖"放大成"假宕机"，比不熔断还糟（不熔断尚有 50–75% 成功）。read=40s（≥依赖 P95）时熔断安静，6/6 全部成功，且 login P99 三档恒为 27ms——**隔离对 login 的保护与 read 取值无关**。

**结论**：
1. read 超时必须 ≥ 依赖延迟 P95/P99，否则熔断的失败率信号失真（慢≠坏）——超时对齐应来自延迟分布测量（Q1），不是拍脑袋常数；
2. login SLO 完全由隔离承担（三档全部 27ms），read 只决定 AI 可用性形态：40s=慢而全活，12s=快而几乎全死；
3. deferred(用户时钟) 与 read(资源时钟) 必须显式分层设置：deferred ≥ read 才不会出现"用户已 504、线程仍被钉"的资源浪费窗口（病理演示见下）。

### 超时分层病理演示（离线确定性）

**数据 2（离线确定性病理演示，`evidence/q3-timeout-layering-demo-20261014.txt`）**：
fake 上游固定 40s、read=40s、deferred=15s、pool=2/queue=0：

| 时刻 | 观测 |
|---|---|
| t=15.6s | 两个用户请求均 504（deferred 超时；onTimeout 已调用 `future.cancel(true)`） |
| 全程 | /api/login 34ms 存活 |
| t=20s | 新请求 **503 in 5ms**（AI_BUSY）——用户已全部超时，但 2 个池线程仍钉在读上，池满拒绝 |
| t=42s（上游 40s 返回后） | 新请求 **200 in 539ms** —— 池线程释放，立即恢复服务 |

**结论（分层语义）**：三个时钟各管一件事——connect 管"连不上"（真实 API 建连+TTFT<1s，从未触发）；read 管"资源释放 + 熔断失败信号"（**不可中断**，cancel(true) 对阻塞 socket read 无效，t=20s 的 503 即证据）；deferred 管"用户等多久"（只结束等待，不回收线程）。deferred 必须 ≥ read，否则产生"用户已放弃、资源仍被烧"的窗口（本例 15.6s→40s，浪费 61% 占用时长）。

## Q4 熔断参数扫描：wait 与半开许可怎么选？（离线确定性）

**假设**：对 26s 级慢依赖，恢复时延存在结构性下限（半开探测本身要跑完一次调用）；过短的 wait 只烧探测配额不缩短恢复，过长则上游恢复后用户仍被降级。

**实验**：`scripts/research/sweep_breaker.py`——fake 上游 26s 延迟，t=0 起 429 故障、t=50s 恢复，3s 节奏单发探测，5 组参数（`evidence/breaker-sweep-20261014-*.jsonl`）。

**数据**：

| wait | 半开许可 | 恢复时延（上游恢复→首个 200） | 恢复后仍被降级 | 故障期浪费的上游调用 |
|---|---|---|---|---|
| 2s | 2 | **27.3s** | 0 | **17** |
| 10s | 2 | **27.3s** | 0 | 8 |
| 30s | 2 | 48.3s | 7 | 6 |
| 10s | 1 | 33.3s | 2 | 7 |
| 10s | 5 | 27.2s | 3 | 11 |

**结论**：
1. **恢复时延下限 = 依赖 P50**（本例 26s 探测 + ~1.3s 调度）：wait=2s 与 wait=10s 恢复完全相同（27.3s），但 wait=2s 在故障期多烧 2 倍探测调用（17 vs 8）——**比探测完成时间还短的 wait 纯属烧配额**；
2. wait=30s 把恢复拖到 48.3s，且上游已恢复后仍有 7 个用户请求被无谓降级——"熔断太懒"直接变成可用性损失；
3. 半开许可=1 使恢复串行化（33.3s），=5 不再缩短恢复（27.2s）但多烧探测；**=2（恰好凑满关闭判定的成功对）最优**；
4. 由此熔断参数改为可配（`ai.breaker.*`，本轮代码变更），推荐 26s 级依赖 wait≈10s、半开=2。

## Q5 有界池容量扫描：池大小决定什么？（离线确定性）

**假设**：池容量只改变 AI 好吞吐与拒绝形态，不影响 login SLO（隔离成立）；队列深度对 26s 级依赖是"慢失败"的温床。

**实验**：`scripts/research/sweep_pool.py`——fake 上游 26s，optimize 需求 10 并发 / login 4 并发 / 100s，5 组容量（`evidence/pool-sweep-20261014-*.md`）。

**数据**：

| pool.max | queue | optimize 200 | 503 | 504 | optimize P50 | login P99 |
|---|---|---|---|---|---|---|
| 2 | 0 | 8 | 783295 | 0 | 1ms | **32 ms** |
| 4 | 0 | 16 | 757414 | 0 | 1ms | **32 ms** |
| 8 | 0 | 32 | 780295 | 0 | 1ms | **36 ms** |
| 16 | 0 | 40（=需求上限） | 0 | 0 | 26.0s | **31 ms** |
| 8 | 50 | 24 | 0 | 14 | 26.1s（P99 36s） | **31 ms** |

**结论**：
1. **login P99 在所有容量下恒为 26–36ms**——隔离与容量完全正交，S1 的核心承诺对任意小池都成立；
2. AI 好吞吐 = pool ÷ 26s（2→8 次、4→16、8→32、16→需求 40 封顶），快速失败路径自身可承 780k 次/100s（≈7.8k QPS）；
3. **队列是 26s 依赖的假慈悲**：queue=50 把 78 万次"1ms 拒绝"换成 14 次"等 36s 再 504"——deferred(35s) < 2×P50(52s) 时排队请求数学上必然超时，排队只是把失败延迟并占用更久（Little's law：等待=深度×26s）；
4. 池上限的真实约束不在 Tomcat 而在上游并发容量（见 Q6）与配额：pool 超过上游并发上限的部分只会生产 429/超时。

## Q6 端点并发容量：每流速率会随并发衰减吗？

**假设**：若端点按流限速，并发升高时单流 tok/s 下降；若并行良好，则池并发可线性放大聚合吞吐。

**实验**：真实 API 单轮 burst（max_tokens=256 界定时长），并发 4 与并发 8 各一次（`evidence/q6-concurrency-20261014.jsonl`，研究纪律 ≤10）。

**数据**：

| 并发 | 成功 | 429 | 单流 tok/s | 聚合 tok/s（估） |
|---|---|---|---|---|
| 4 | 4/4 | 0 | 18.7–23.0 | ~80 |
| 8 | 8/8 | 0 | 18.5–25.2 | ~160 |

**结论**：
1. 并发 ≤8 时**单流速率不衰减**（与串行 13–24 tok/s 同域），聚合吞吐随并发线性放大——池并发是免费的吞吐杠杆（受配额与更高并发未测的限流约束；>10 并发违反本研究纪律，未测，如实留白）；
2. 结合 Q5：池容量应设为"上游可承受并发 × 安全系数"，而非 Tomcat 线程数——本订阅实测 8 并发无限流。

## Q7 质量保持下的延迟下限：截断换速度的边界在哪？

**假设**：完整回答需要 ~250–716 token（Q1 实测），则质量无损的延迟下限 = 所需 token ÷ 生成速率，无法用任何工程手段低于此值。

**实验**：max_tokens=768（≥历史最大需求）×3，看 finish_reason 与延迟（`evidence/q7-quality-floor-20261014.jsonl`）；对照 Q2 的 32/128 截断数据。

**数据**：

| max_tokens | finish_reason | completion_tokens | 延迟 |
|---|---|---|---|
| 32 | **length（4/4 截断）** | 32 | 1.4–2.3s |
| 128 | length 3/4 截断 | 55–128 | 3.7–7.5s |
| 768 | **stop（3/3 完整）** | 248/604/543 | 11.0 / 32.2 / 28.6s |
| ∞（Q1, n=18） | stop | 40–716 | P50 17.9s / P95 47.5s |

**结论**：
1. `max_tokens=768` 是无损上限：全部自然 stop，延迟 P50 28.6s——与不设上限的 P50 17.9s 同量级，**质量保持的延迟下限 ≈ 所需 token × 61ms，由模型生成速率单方面决定**；
2. 想要 2s 级延迟（max_tokens=32）必然 100% 截断——"快"与"完整"在这类模型上是硬权衡，中间档（128）也 75% 截断；
3. 唯一未试的工程杠杆是指令级约束（"50 字以内"）——但那改变的是任务本身（模型少写），不是让模型写快，属产品取舍而非工程压缩。

## 总结：瓶颈与工程含义

**瓶颈（一句话）**：glm-4-flash 的生成速率 ≈16.4 tok/s（13–25，r=0.974 线性，截距≈0）且输出长度非确定（同提示词 40–716 token，CV=0.82）——**质量保持的单调用延迟下限 = 所需 token × 61ms，P50≈18–29s、P95≈48s，不可被连接池/超时/熔断/并发任何工程手段压缩**；并发只线性放大聚合吞吐，不改变单流时延。

三问收敛验证（停止条件）：Q2（速率斜率）、Q6（并发不衰减单流速率）、Q7（无损下限=token×61ms）从三个独立实验收敛到同一模型侧硬限。

**工程含义（全部有实验背书）**：

| 层 | 数据驱动的配置法则 |
|---|---|
| read 超时 | ≥ 依赖 P95（本依赖 40s+）：12s 会把 50% 成功变 0.002% 用户成功（Q1+Q3） |
| deferred | ≥ read，否则"用户已弃、线程仍烧"（Q3 演示：15.6s 弃、40s 才释放，61% 浪费） |
| 熔断 wait | 5–10s：短于探测时长纯烧配额（17 vs 8 次调用，恢复同为 27.3s）；过长则恢复后仍误杀（Q4） |
| 半开许可 | 2：1 串行化恢复（+6s），5 无增益多烧探测（Q4） |
| 池容量 | 上游并发容量决定（实测 8 并发无限流），与 login SLO 无关——login P99 恒 26–36ms（Q5/Q6） |
| 队列 | 慢依赖慎用：deferred < 深度×P50 时排队必然超时，是延迟化的失败（Q5） |
| max_tokens | 延迟旋钮但有损：32→2s 但 100% 截断；768→无损 P50 28.6s（Q2/Q7） |

**本轮代码变更**（均带测试，`mvn test` 7 项全绿）：
1. `ai.breaker.*` 五参数可配（原硬编码）——Q4 扫描的前提；
2. `ai.llm.max-tokens` 请求体旋钮——Q7 的延迟/质量权衡入口；
3. deferred ≤ read 启动告警——Q3 发现的分层错配的可见化；
4. deferred 超时 `future.cancel(true)` + `isSetOrExpired` 守卫——尽力短路回调与写回（资源上界仍由 read 决定，Q3 演示证明 cancel 不能释放线程）；
5. 删除死代码 `AiProperties.getMax2()`。
